# Хранение расписаний бригад в БД (проект)

Это черновик решения, ничего из него пока не реализовано. Таблица для сохранения расписания в CLAUDE.md помечена как «создаётся позже».

## Идея

В БД хранится то же, что и в памяти: **только различия**, и каждая строка привязана к номеру версии (`VER_ID`).

Версия в БД — это «снимок» (snapshot): строки о сменах, правках смен, переходах и отпусках одной версии. Версия в памяти (`CrewSchedule`) остаётся рабочей копией пользователя и попадает в БД при нажатии «Сохранить». Данные месяца небольшие (десятки смен на линию), поэтому копировать их целиком при каждом сохранении дёшево и просто.

## Таблицы

Все таблицы, кроме первой, содержат `VER_ID`.

| Таблица | Что хранит | Соответствует в `domain/` |
|---|---|---|
| `PLR_SCHED_VER` | `VER_ID`, `MONTH`, название, статус (`DRAFT`/`PUBLISHED`), кто и когда создал, `BASE_VER_ID` (от какой версии скопирована), `ROW_VERSION` | `CrewSchedule` |
| `PLR_SCHED_SHIFT` | `VER_ID`, дата, тип (DAY/NIGHT), линия, бригада `BRID`, `PINNED` | `CrewShift` |
| `PLR_SCHED_SHIFT_EMP` | `VER_ID`, смена, `TABN`, вид: `ABSENT` или `EXTRA` | `absentEmployees`, `extraEmployees` |
| `PLR_SCHED_SHIFT_ROLE` | `VER_ID`, смена, `RLID`, `NPERS` (только для смен с изменённым составом) | `composition` |
| `PLR_SCHED_CREWCHG` | `VER_ID`, `TABN`, `FROM_DATE`, `BRID` | `crewChanges` |
| `PLR_SCHED_ABSENCE` | `VER_ID`, `TABN`, тип, `FROM`, `TO` | `absences` |

Ключ смены — три колонки `дата + тип + линия`. Это то же самое, что `id = date-TYPE-lineId` в коде.

Итоговый состав смены в БД **не хранится**. Он считается при загрузке по правилам из `CrewShift.getEmployees()`:

```
люди смены =
    (сотрудники бригады, которые в эту дату реально в бригаде
     и не в absentEmployees)
  + extraEmployees
  − те, у кого в эту дату отпуск, больничный или увольнение
```

Поэтому перевод сотрудника в другую бригаду по-прежнему записывается одной строкой в `PLR_SCHED_CREWCHG`, а все его смены пересчитываются сами.

## Как это работает

- **Сохранить:** в одной транзакции записать строки версии (для новой версии новый `VER_ID`).
- **Загрузить:** прочитать строки по `VER_ID` и собрать `CrewSchedule`. Нужен метод рядом с `CrewScheduleFactory`, который строит объект из таблиц вместо копирования другого объекта.
- **Новая версия на основе старой:** `INSERT ... SELECT` с новым `VER_ID` и записью `BASE_VER_ID`.
- **Опубликованная версия** (по ней идёт экспорт в «Табельный учёт») не меняется. Изменения делаются в новой версии, так история сохраняется сама.
- **Параллельное сохранение:** если `ROW_VERSION` при сохранении не совпала, значит версию уже кто-то сохранил, и пользователь получает ошибку 409. Это аналог `versionId` в `CrewScheduleRepository`, только в БД.
- Для вставок использовать пакеты (batch), а не `IN (:ids)`: в SQL Server не больше 2100 параметров на запрос.

## История «кто и что менял»

Снимок отвечает на вопрос «каким было расписание», но не на вопрос «кто и когда сдвинул смену». Если это нужно, добавить журнал `PLR_SCHED_LOG` (`VER_ID`, время, пользователь, операция, JSON параметров).

Все правки проходят через `CrewScheduleSessionService.edit`, поэтому писать журнал нужно только там.

Хранить только журнал и пересобирать расписание повтором операций не стоит: загрузка медленнее, а старые записи придётся поддерживать при любом изменении правил редактора.

## Ловушка: данные вне версии

Состав бригады по ролям (`PLR_RLBR`) и сотрудники в бригаде (`PLR_TBBR`) живут вне версии и меняются со временем. Версия хранит только `BRID` и `TABN`, поэтому старая версия через полгода может загрузиться с другим составом бригад.

Варианты:
1. **Принять это** для черновиков.
2. **При публикации** дополнительно записывать копию состава на тот момент (например, `PLR_SCHED_CREW_EMP`: `VER_ID`, `BRID`, `TABN`, `NPERS` по ролям). Рекомендуется для опубликованных версий.
